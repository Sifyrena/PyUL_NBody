- 22 Sep 2026: FEATURE: Added `BondiHoyleCalibration(M, v, cs=0.0)` to `Particles/Accretion.py` — derives `Sink.Amplitude`/`Sink.Radius` that make `ApplySink`'s early-time absorption rate reproduce the classical Bondi-Hoyle-Lyttleton rate `Mdot = 4*pi*(GM)^2*rho/(v^2+cs^2)^1.5` (G=1, code units): `Radius = 2M/(v^2+cs^2)` (Bondi radius), `Amplitude = (v^2+cs^2)^1.5/(8*sqrt(2*pi)*M)`. - 22 Sep 2026: FEATURE: `Sink.Dynamic` (config.BlackHole["Sink"]) — when `True`, `ApplySink` ignores the fixed `Amplitude`/`Radius` and recomputes them every step from the sink particle's *current* mass and speed via `BondiHoyleCalibration()`, so a particle on a bound/oscillating orbit (like `BHAccretionDemo.uldm`) gets a genuinely time-varying, locally-correct accretion rate instead of one fixed snapshot value. Speed is floored at `Sink.VFloor` (default 0.05) to keep the Bondi radius finite at orbital turning points, and `Radius` is separately capped at `Sink.RadiusCap` (default `0.25*BoxLength`) since `R ~ M/v^2` can otherwise run past the box as the sink grows and slows — capping `R` alone (not `Amplitude`) under-delivers relative to the naive divergent rate, which is the standard low-velocity regularization for sink particles. `BHAccretionDemo.uldm` now uses `Dynamic=True`.

- 23 Sep 2026: FEATURE: `Sink.ConserveMomentum` (config.BlackHole["Sink"]) — the sink was previously a pure mass leak: it grew the particle's mass with zero recoil, unphysical since real accretion carries a drag force set by the relative velocity of the swallowed gas. Fixed by depositing the absorbed ULDM's momentum onto the particle. Derivation: `psi *= exp(-h*V_sink)` is a real multiplicative factor, so it rescales amplitude but leaves phase - and therefore the local velocity field `v(x)=j(x)/rho(x)` with current density `j=Im(psi* grad psi)` - unchanged. The momentum removed is `integral of j(x)*(1-exp(-2*h*V_sink(x))) dV`, computed via a spectral (FFT) gradient of psi, and added to the particle's momentum (mass-weighted, then divided by the new mass - a rocket-equation update since mass and velocity change together). Costs 3 extra FFTs per step (`np.fft.fftn`/`ifftn`, not the existing pyfftw plans - kept separate for simplicity/correctness). `BHAccretionDemo.uldm` now sets `ConserveMomentum=true`.

- 23 Sep 2026: VALIDATION: built a direct check of total (field + particle) momentum conservation - ran the same soliton-eating setup three ways (48³, short duration) and computed `integral(Im(psi* grad psi)) + M*v` at every save from saved wavefunction snapshots. Gravity-only baseline (no sink at all) has residual numerical drift ~1e-3 (grid/interpolation noise, not a bug). Sink **without** `ConserveMomentum`: drift -0.35 (~310x the gravity floor - confirms the leak was real and large). Sink **with** `ConserveMomentum`: drift +0.0055 (~5x the gravity floor) - a 64x improvement, landing close to the pre-existing numerical noise floor rather than at machine precision. The residual gap is worth understanding better (candidates: finite-h discretization in the momentum integral, or it's simply consistent with the same grid/interpolation noise the baseline shows) but this is strong confirmation the fix works as intended. Re-ran `BHAccretionDemo.uldm` at resolution 64 with `ConserveMomentum=true`: mass conservation still exact (1.6e-12), but the growth curve changed materially (final mass 0.735 vs. 1.55 without momentum feedback) since the particle now genuinely feels drag/kicks from what it swallows instead of gaining mass for free. Plots updated in place.
- 24 Sep 2026: BUGFIX (inherited from "The Original PyUL NBody"): `FWNBody`/`FWNBody_NI` in `Integration/NBodyAdvance.py` silently zeroed the particle's gravitational force from the ULDM field whenever it came within ~2 grid cells of any box face, instead of erroring or wrapping - a numerical safety net mistaken for physics. For a periodic domain (`BC.IsoP=False`, the common case) this is wrong: the field genuinely continues across the boundary. Fixed by wrapping the local 4x4x4 force-interpolation patch periodically (`np.arange(...) % resol`) whenever `IsoP=False`; the old hard-zero fallback is kept for `IsoP=True` (isolated/vacuum potential), where there's no periodicity to wrap into. `NBodyAdvance`/`NBodyAdvance_NI` gained a `Periodic` parameter (`Evolve.py` passes `Periodic = not IsoP`), defaulting to `True` to match the periodic case that's actually common. Applies to every run with matter particles, sink or not. Verified with a synthetic sinusoidal-potential unit test (force near the edge now tracks the analytic gradient instead of reading zero) and confirmed byte-identical output for particles away from the boundary (the existing smoke test's particle never approaches the edge).
- 24 Sep 2026: BUGFIX: the BH sink (`ApplySink`) was being applied to `psi`/`rho` at the particle's position from the *end of the previous step*, while the Newtonian back-reaction `phiTM` the field feels is (correctly) built at the particle's freshly-advanced position later in the same step - a one-substep temporal mismatch between the sink's imaginary-potential channel and the real/gravitational channel. Fixed by moving the `ApplySink` call in `Evolve.py`'s main loop from just after `rho` is recomputed to just after `NBodyAdvance`/`NBodyAdvance_NI`, so absorption and `phiTM` are now evaluated at the same position. Side effect: the Poisson solve that determines the particle's own motion this step now uses the pre-absorption density (mass not yet swallowed still gravitates on the particle as it approaches - a defensible physical reading: absorption and its Newtonian deposit happen together at the step's end, co-located with the particle's arrival position) rather than the post-absorption density used previously. No effect when `Sink.Flag=False` (the block is a no-op) - confirmed via the existing smoke test, which reproduced the exact non-sink mass-conservation baseline and the sink case's mass-conservation to ~1e-8 relative of the previous run's numbers (the tiny difference is the intended physics change, not noise).
- 29 Sep 2026: BUGFIX: `Sink.Dynamic`'s Bondi-Hoyle calibration used the sink particle's raw speed in the box/grid frame, but the classical BHL rate is defined with the relative velocity between the accretor and the ambient medium - only equivalent when the local ULDM has no bulk motion of its own. That assumption is violated by the very mechanism this codebase's own literature review turned up: an orbiting BH generically excites a coherent dipole oscillation (bulk motion) in the soliton it orbits (Zhang, Wang, Zagorac & Easther 2026, arXiv:2602.11512, "stone skipping"). Added `Sink.RelativeVelocity` (default `false`, opt-in): when set, interpolates the local ULDM current `j(r)/rho(r)` at the particle's position (reusing the spectral current already computed for `ConserveMomentum`, or computing it fresh if that's off) and uses `v_particle - v_local` in the `BondiHoyleCalibration` call instead of raw `v_particle`. `rho(r)` is floored to avoid a 0/0 blowup at wavefunction nodes, falling back to the old grid-frame behaviour locally rather than producing a meaningless velocity. **Empirically confirmed material, not academic**: re-ran `BHAccretionDemo.uldm` (`Dynamic=true`, `ConserveMomentum=true`) with `RelativeVelocity` off vs on - accreted mass differs by up to +2.3% mid-run, settling to +0.9% by the end, systematically in the same direction at every single comparison point (not noise). This is larger than the ~0.1% effect from the 24 Sep temporal-ordering fix. No effect on `Dynamic=False` runs or when the local field genuinely has no bulk motion (e.g. the earlier 7-point BHL calibration scan, which used a uniform background at rest and so could never have exercised this code path either way).

- 30 Sep 2026: BUGFIX (serious, caught before it reached a real run): `ApplySink`'s current-density calculation (needed for `ConserveMomentum`/`RelativeVelocity`) originally used plain single-threaded `np.fft.fftn`/`ifftn`, four transforms every step, while the rest of the solver uses `pyfftw` with all CPU threads - a real slowdown (observed 615%->227% CPU on an otherwise-identical run). First attempted fix reused the main loop's existing `fft_psi`/`ifft_funct` pyfftw plan objects to avoid the extra threading setup. That introduced a far worse bug: the main loop does `psi = ifft_funct(funct)` with no copy, so `psi` is an alias of `ifft_funct`'s own persistent output buffer for the rest of the step - calling `ifft_funct` again from inside `ApplySink` (three times, for the three current components) silently overwrote that buffer, corrupting the live `psi` *before* the sink decay was applied. Manifested as the sink particle's mass exploding from 3.4 to -1.8e5 on the very first `ApplySink` call and diverging further from there, eventually crashing `NBodyAdvance` with a garbled index error many steps later - confirmed via direct tracing (dumped the real `psi`/`rho`/k-arrays at the first sink call and replayed offline) and a minimal repro (`ifft_funct(a)` then `ifft_funct(b)`: the first call's returned array silently changes value after the second call, same object every time). Fixed by giving `ApplySink` its own dedicated `fft_sink`/`ifft_sink` pyfftw plans (built once in `Evolve.py`, only when the sink actually needs the current density), never touching the main loop's `fft_psi`/`ifft_funct` buffers. Verified: mass now grows smoothly (3.406 -> 3.821 over 85 steps on the stone-skipping accretion config, no blowup) and CPU usage is back to ~515%. This bug never reached a saved/reported run - caught during the first attempt to turn accretion on for the stone-skipping campaign, before any results were taken from it.

- 5 Oct 2026: BUGFIX (NumPy compatibility): `FWNBody`/`FWNBody_NI` in `Integration/NBodyAdvance.py` built the local gradient as a `(3,1)` array (`np.array([[GradientX],[GradientY],[GradientZ]])`), so `GradientLocal[0]` was a size-1 array being assigned into scalar slots of `dTMdt`/`GradientLog`. That conversion has been deprecated since NumPy 1.25 and raises `ValueError: setting an array element with a sequence` on stricter NumPy versions (reported on a user laptop; NumPy 2.2.0 only warns). Now a flat `(3,)` array - behavior-identical, since it is only ever indexed `[0]/[1]/[2]`. Verified a short full run (sink on) with `DeprecationWarning` escalated to an error.
- 6 Oct 2026: FEATURE: `Sink.RateScale` (default `1.0`, `Dynamic` mode only) multiplies the BHL-calibrated sink amplitude, leaving the kernel radius at the Bondi radius, so the absorption rate is `RateScale x Mdot_BHL`. Motivation: BHL (a dissipative-gas capture rate) overestimates absorption of collisionless wave dark matter by ~5e8 (classical horizon capture, ratio (c/2v)^2) to ~2e13 (Unruh wave-regime cross section, verified against Bar, Blum, Eby & Sato 2019, arXiv:1905.11745 Eqs. A18-A19) for the stone-skipping setup (m22=10, v~6.4 km/s); the physical rate relative to BHL is f = 4 S(zeta) (v/c)^3 ~ 5e-14. With `RateScale=1` the sink reproduces the BHL rate it was calibrated to (5.5e-3 vs 5.2e-3 Msun/yr early on) - a calibration check, not evidence BHL is physical - so the 5.7x BH growth in the earlier stone-skipping accretion runs is an artifact of that normalization. Also corrected: the code mass unit at m22=10 is 7.05e4 Msun, so the BH grew 0.24 -> 1.37 x 1e6 Msun (earlier plots labelled code-unit values as 1e6 Msun). `Scripts/rate_scan.py` runs one scan point per call (SLURM-array friendly). Configs `StoneSkipping_Baseline_{NoAccretion,Accretion,Accretion_256}.uldm` added.
